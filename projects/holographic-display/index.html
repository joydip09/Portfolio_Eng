Prototype Experimental ESP32 POV

DIY Holographic Display

A persistence-of-vision LED cylinder spinning at 600 RPM — rendering text and shapes as floating 3D-like images in mid-air, for under ₹2000 in parts.

ESP32 WS2812B LEDs Hall Effect Sensor Slip Ring Brushless Motor 3D Printed Frame
01 — Problem

The Idea

I'd seen commercial POV (persistence-of-vision) displays online — spinning LED arms that trick your eye into seeing a complete 2D image floating in space. Proper holographic volumetric displays cost thousands. But a POV display? That felt buildable.

The core question: could I spin an LED strip fast enough that human persistence of vision would fill in the gaps, rendering a coherent image from discrete flashes of light? The answer, it turns out, is yes — but the engineering to get there is genuinely hard.

🧠
How POV Works
The human eye retains an image for roughly 1/25th of a second (the persistence of vision effect). If an LED arm completes one full rotation faster than this, and lights specific LEDs at precise angular positions, the brain assembles the flashes into a complete circular image.
02 — Planning

Design & Architecture

The system has three interdependent challenges that all had to be solved together:

  • Mechanical — Spin an LED arm fast and stably enough at 600+ RPM
  • Synchronisation — Know exactly where the arm is at every millisecond
  • Data transfer — Get power and control signals onto a spinning assembly

Synchronisation Approach

A Hall effect sensor mounted on the fixed base detects a neodymium magnet attached to the spinning arm once per revolution. This pulse resets the angular position counter, ensuring each rotation starts at the same reference point regardless of speed variation.

The Slip Ring Problem

You can't run wires to a spinning assembly — they'd twist and snap. A 6-wire slip ring provides continuous electrical contact between the static base and the rotating frame. Two wires for 5V power, one for GND, one for the WS2812B data line.

05 — Implementation

Firmware & POV Rendering

Each frame is stored as a 2D array: 18 rows (LEDs, radial position) × 120 columns (angular slices around the circle). At 600 RPM, one revolution takes 100ms. Divided into 120 slices gives ~0.83ms per column — tight but achievable with ESP32.

The Hall sensor interrupt fires once per revolution, resetting the column counter and recalibrating the timing interval based on the measured period.

C++ (ESP32 Arduino) Copy 
#define NUM_LEDS     18
#define NUM_COLUMNS  120

CRGB leds[NUM_LEDS];
uint8_t frame[NUM_COLUMNS][NUM_LEDS][3]; // R, G, B per pixel

volatile unsigned long lastHallTime   = 0;
volatile unsigned long rotationPeriod = 100000; // µs, initial guess
volatile int currentColumn = 0;

// Hall sensor interrupt — fires once per revolution
void IRAM_ATTR onHallPulse() {
  unsigned long now = micros();
  rotationPeriod    = now - lastHallTime;
  lastHallTime      = now;
  currentColumn     = 0; // reset angular position
}

void loop() {
  unsigned long columnDuration = rotationPeriod / NUM_COLUMNS;
  unsigned long nextColumnTime = micros() + columnDuration;

  // Render current column
  for (int i = 0; i < NUM_LEDS; i++) {
    leds[i] = CRGB(
      frame[currentColumn][i][0],
      frame[currentColumn][i][1],
      frame[currentColumn][i][2]
    );
  }
  FastLED.show();

  currentColumn = (currentColumn + 1) % NUM_COLUMNS;

  // Busy-wait for precise column timing
  while (micros() < nextColumnTime);
}
⏱️
Timing is Everything
At 600 RPM, each of the 120 columns must be rendered in ~0.83ms. FastLED's show() takes ~0.5ms for 18 LEDs at 800kHz. This leaves only ~0.33ms for computation — which is why a busy-wait loop is used instead of delay().
06 — Troubleshooting

Failures & Fixes

🌀
Image "Smears" at High RPM
At 800+ RPM, the image started smearing into arcs instead of clean columns. Root cause: FastLED.show() latency was eating into column timing. Fix: reduced to 600 RPM (more stable) and pre-computed all column timings rather than recalculating each revolution.
⚡
Slip Ring Introducing Data Corruption
WS2812B data signal was getting corrupted through the slip ring at speed — motor EMI coupling into the data wire. Fix: shielded the data wire with foil, added a 100nF decoupling cap close to the LED strip VCC, and kept data wire away from power wires in the slip ring bundle.
⚖️
Severe Vibration — Imbalanced Arm
The 3D-printed arm was slightly asymmetric — at speed it vibrated badly enough to walk across the table. Added small M3 nuts as counterweights to the lighter end, iterating until vibration was eliminated at operating RPM.
🔄
Hall Sensor False Triggers
Motor magnets were triggering the Hall sensor multiple times per revolution. Fixed by repositioning the sensor further from the motor and adding a 10ms software debounce on the interrupt — any pulse within 10ms of the last is ignored.
07 — Results

Current State

  • Resolution: 18 LEDs × 120 columns = ~2160 pixels per frame
  • Rotation speed: ~600 RPM stable
  • Frame rate: ~10 FPS at current sync accuracy
  • Text rendering: Clean, readable up to 3–4 characters
  • Complex images: Recognisable but needs better angular calibration

🚧
Still a Prototype
This project is ongoing. The mechanical and electrical foundations work well — the main remaining challenge is software: improving angular calibration, adding a Wi-Fi image upload interface, and achieving stable 30 FPS rendering.
08 — Reflection

What I Learned

This is the hardest project I've built so far. It sits at the intersection of mechanical engineering, real-time firmware, signal integrity, and optics. Each domain had its own failure modes that I had to research and solve independently.

The EMI interference from the motor into the data line was completely unexpected — I didn't think of the slip ring as an antenna until I started reading about brushless motor EMI. That rabbit hole led me to understanding shielding, decoupling capacitors, and ground planes in a much more practical way than any tutorial had.

Next Steps

  • Design a custom PCB for the spinning assembly — reduce weight and improve signal integrity
  • Implement Wi-Fi frame upload — send images directly from phone to ESP32
  • Add a second LED arm (180° offset) to double the resolution
  • Explore cylindrical 3D rendering — stack frames at different heights for true volumetric effect
  • Investigate encoder-based position sensing for better angular accuracy than Hall sensor alone
